Homelab platform

I rebuilt my home server from a pile of hand-managed containers into 36 Compose stacks in git. A validator has to pass before anything deploys, the new stack ran next to the old one during the migration, and the AI agents run in containers designed around what they can't reach.

Why rebuild

When I took stock of the old lab, the list was bad. The nightly backup script failed with an error on every run and had never produced a copy, so the container manager's own database had never been backed up. More than 17 images ran on floating tags, and an auto-updater had broken services three times by pulling new versions nobody had reviewed. The password vault wasn't defined in any compose file. Several exited containers had been granted full privileges to administer the host from inside, and there were about thirty leftover project directories that nobody could explain.

I decided not to repair it. The plan treated every service as replaceable and only the data as precious. I wrote it as a phased build plan with a verification gate at the end of each phase. Two days in, I lost a photo library during a data move: a mv across two bind mounts turned into a copy-then-delete, and I then removed what I thought was a partial copy. Nothing was backed up, and that was the real root cause. That's why backups were the first thing built, before any service moved.

Policy as code: the deploy gate

deploy.sh runs validate.sh first and exits if it fails. The validator checks every stack for the following:

  • It parses the way Docker parses. It uses a strict YAML check that rejects duplicate keys. The first version used a lenient parser, and a broken file got through as a PASS.
  • An x-homelab contract block with tier, wave, data_class and purpose.
  • Every image is pinned by @sha256 digest. A floating tag is a hard failure. A locally built image (7 stacks) is only accepted if the file declares an unpinned_reason. That way the exception is written down in the stack itself, not tucked away in the validator.
  • The homelab.managed label is present. The edge proxy won't route to anything without it.
  • No plaintext credentials anywhere in stacks, policy, host config or scripts. The scan has a tested list of exclusions (variable references, placeholders, lock files, version ranges), because a gate with false positives ends up switched off.
  • Every .env file is ignored by git, checked with git check-ignore rather than assumed.

A typical contract block, lightly trimmed:

x-homelab:
  tier: auto
  wave: 2
  data_class: replaceable
  backup_paths: []      # model weights are a download, not data
  depends_on_host: []
  purpose: Local LLM runtime - alert triage and the chat UI, sharing one model.

services:
  ollama:
    image: ollama/ollama@sha256:6b08…8966
    mem_limit: 22g
    cpus: 8.0
    labels:
      homelab.managed: "true"
      homelab.tier: auto
      homelab.wave: "2"

The deploy script also learned from a failure. If a stack bind-mounts its own code, compose up won't recreate it after a git pull, so the old code keeps running while the deploy reports success. Stacks like that now name the services to restart in restart_on_deploy. They list individual services, not the whole stack, so the notification queue doesn't get dropped just to reload one Python file.

Architecture

A few design choices worth mentioning:

  • The raw Docker socket is mounted in exactly one place, a read-only socket proxy. Everything else, the edge proxy included, talks to that. On a Docker host, socket access is root.
  • SSO is a front door, never the only door. The dashboard, the alert channel, the password vault and the proxy itself are deliberately kept out from behind it, so you're never locked out of your diagnostics during an outage.
  • Self-healing uses a lookup table, not a model. The watcher's verbs go through a second socket proxy that allows only inspect, restart and start. DELETE isn't enabled at all, and restarts are rate-capped. The local model gets the alert text and writes a plain-English summary. It isn't asked what to do, and it has no way to act on an answer.
  • Backups are add-only. Stack data is mounted read-only and replicated without --delete. Encrypted, versioned restic snapshots sit on top of that, and every backup writes a heartbeat that gets monitored.

Migrating without downtime

The old lab kept serving the house the whole time. The two sides were set up so they couldn't interfere with each other:

Legacy

  • Managed through a container-manager UI
  • Mixed networks and names
  • Floating tags plus an auto-updater
  • No marker for what belonged where

Rebuilt

  • Compose files in git, deployed by script
  • Its own network, name prefix and data directory
  • Pinned digests only
  • A homelab.managed label the edge proxy filters on, so a legacy container can't be exposed by accident

Each service follows the same steps: stand it up against a copy of the data, verify it, quiesce the old one, sync the delta, then switch over. The old instance stays stopped but intact as the rollback. A service only retires after a soak period, once its backups verify from the new side and nothing still pending depends on it. The old proxy, for example, was only retired after every name returned the same status through the new edge as through the old one.

One lesson from this part: docker stop isn't retirement. A daemon restart brought three "retired" containers back because of restart: always, and for a while two copies of one service were running against different databases. Retiring now means setting the restart policy to no and then stopping the container, never removing it.

Sandboxing AI agents

Two stacks run model-driven shell commands: a chat-to-Claude-Code bridge and a work-board service that takes issues from a Linear backlog and hands them to agents. Both are built around what they must not be able to reach:

  • No Docker socket and no membership in the small internal network where the restart-capable proxy lives. Restarting a container simply isn't possible from inside.
  • No NAS mounts, no other stacks' data, and no checkout of the repo that deploys them. An agent can't edit its own guardrails.
  • One workspace directory. The chat bridge refuses to start without a user allowlist.
  • Read-only git credentials. Agent work goes to a branch on the self-hosted git server, never to the main branch.
  • Hard refusals on spend: per-hour and per-day job caps, plus a share of the subscription window held back for my own interactive use.

The biggest lesson was that a comment describing isolation is not isolation. One stack's header said it had no path to the Docker API. When I tested that claim from inside the container, a restart request went through, because the proxy's allowlist covered the whole lab network. The proxy now sits on a dedicated internal network with a single peer, and I test isolation claims from inside the container. The same thinking applies to the pipeline itself: an issue used to close when its last stage finished, even if that stage had reported it couldn't do the work. Now it closes only on a recorded verdict with evidence.

What I'd do next

  • Move the gate into CI. validate.sh is written as the local version of a CI pipeline. Next is running it on a self-hosted runner, alongside secret scanning, per-digest image scanning and automated digest-bump PRs. Pinning stops silent breakage, but it also stops silent security updates, so it needs a scanner next to it.
  • Enforce the authority tiers. The path-to-tier map already exists as policy. Branch protection should enforce it, so changes to policy, host config and scripts always need a human review.
  • Consolidate ownership. A few services still run outside the repo. The rule is "if it isn't in the repo, it doesn't run", and a daily inventory diff should flag anything that breaks it.
  • Encrypt secrets per file and codify the host. That means sops-encrypted secrets in git, and a provisioning playbook so the host itself can be rebuilt from the repo too.
