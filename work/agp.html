AGP: an AI receptionist and automation platform for local businesses

In February 2026 I founded Assisted Growth Partner (AGP) and built its whole technical stack myself: a voice agent that answers and books calls, a multi-tenant automation layer on n8n, and a lead-audit product that shows a business where it is losing leads. It runs in production for paying clients. This page covers what I built, how it fits together, and what I'd do differently.

What it is

AGP sells AI automation to small service businesses, the kind that depend on the phone and lose work when nobody picks up. The core product is an AI receptionist that answers calls, qualifies the caller, books appointments into the client's CRM calendar and hands hot leads to a human. Around it sit outbound follow-up calls, CRM sync, alerting, an ops dashboard, and a sales tool (the Lead-Leak Audit) that shows prospects what missed calls are costing them.

I do all of it, from product and architecture to running the production server.

The AI receptionist

Calls ran on Vapi. When a call came in, Vapi asked my n8n webhook which assistant to use. The real-time handler worked out which client the dialled number belonged to, loaded that client's agent config from Postgres, added context (a caller lookup in GoHighLevel, local weather) and returned a fully built assistant. If it couldn't resolve the client, it returned a safe fallback assistant rather than failing the call.

During the call the agent could use tools I exposed as webhooks:

  • Booking. One workflow checked availability and booked, rescheduled or cancelled appointments in the GoHighLevel calendar, then tagged and annotated the contact.
  • Transfers. A human-transfer route and a sales-transfer route that picked the destination per client.

When the call ended, the handler acknowledged Vapi immediately and passed the work to an async post-call workflow, so slow CRM calls never held up the voice side. That workflow:

  • scored the call with an LLM (Gemini): a hot/warm/cold heat score, adjusted by per-client keyword boosters, plus an outcome classification;
  • wrote the call log (summary, transcript reference, duration, cost) to Postgres;
  • for warm and hot callers, upserted the contact in GoHighLevel, added a note, moved the opportunity stage and set follow-up tags;
  • sent the follow-up email or text through GoHighLevel where the client had turned that on, posted to Slack, and recorded opt-outs in a do-not-call table that also cancelled any queued outbound calls.

Each night a review pipeline ran the day's calls past narrow reviewer agents. A rewriter proposed prompt changes, a QA agent checked them, and the result became a Linear issue for me to review. Nothing was applied automatically.

Multi-tenant automation on n8n

Every client shared the same workflows. What made that work was a resolve tenant + runtime subflow in front of everything. It normalised the incoming payload, looked up the client's config row and returned one runtime object (agent settings, CRM location, routing, notification channels), or an explicit "unresolved" result the caller had to handle.

  • Onboarding and provisioning. Small API workflows behind an onboarding form let a client save and submit their setup. I reviewed it in an admin view, and approving it provisioned the client's config row.
  • Campaign dispatcher. Outbound follow-up calls sat in a Postgres queue. Every minute a dispatcher pulled the calls that were due, checked GoHighLevel to skip anyone who had already been handled, built the payload through a shared subflow, placed the call through Vapi, and marked the row in progress, or failed with a scheduled retry. A result handler closed each row out, and a nightly job reset stuck rows and pruned old ones.
  • Error handling and backups. A shared error workflow logged each failure to Postgres and posted it to Slack. Daily jobs backed up workflows and key tables to a private GitHub repo.
  • Ops dashboard. Small read-only API workflows fed a single-page dashboard with cost, performance, pipeline, billing and alert views. It showed cost per call, per hot lead and per booking, plus stuck calls and clients that had gone quiet.

The Lead-Leak Audit

This was the sales tool: enter a local business, get back a report showing where it leaks leads. It ran as a pipeline of three n8n workflows behind a Next.js app.

  • Intake. A form posted to an intake webhook, which validated the input and ran the two stages below.
  • Engine. This stage pulled Google business-profile data, built a profile scorecard, found the nearest competitor, and ran the "leak math" (an estimate of revenue lost to missed calls). It also rendered a PDF version. An after-hours test call was designed behind a compliance gate.
  • Enrichment. Collectors for reviews, a site crawl, PageSpeed, ad presence, keyword data, map rankings, and "AI visibility": asking several LLM engines for a recommendation and checking whether the business came up.
  • Scoring and report. The scores were deterministic code, not model output. The web report recomputed the headline numbers on the server so they matched n8n exactly, with parity tests to keep it that way. Claude handled the language work: turning free-text engine answers and review text into structured, validated JSON through forced tool calls. A separate eval suite covered the scoring and extraction.
  • Preview site. Claude also generated a one-file preview website for the audited business from the audit data. One pass built the site and a second critiqued and revised it. The prompt told it never to invent reviews, ratings or offers.

Automated outbound outreach is deliberately held behind compliance gates (calling rules, email law, do-not-call) until each piece passes review.

Architecture

Building with agents

Much of the Lead-Leak Audit was built with Agentic Builder, a Claude Code plugin I wrote. It defines 19 role agents (director, planner, coder, AI engineer, automation engineer, data engineer, QA, security, compliance, DBA and others) and a pipeline for handing work between them through shared files: brief, spec, tasks, test reports.

The part I'm most careful about is database access. Only the DBA agent can call the Postgres write tool; every other agent has it on a deny list. On top of that, a PreToolUse hook blocks every write unless I have opened a write window by creating a flag file, and it logs every attempt, allowed or blocked. So a migration only runs when I decide it should, and there is a record of each try.

What I learned

  • Error handling has to be the default. I built a shared error workflow, but attaching it was opt-in, and plenty of workflows never got it. The failures that hurt were the ones with nowhere to report to. Next time it's attached by default and checked before anything goes live.
  • Treat workflow exports like code. Nightly exports to Git gave me history, but they also copied whatever was inside a workflow. Credentials belong in the credential store, and exports should be scanned before they're committed, just like a code repo.
  • Too many generations. I ended up with three copies of the platform (original, a [STAGE] set and a [V3] set), plus several duplicate subflows and throwaway test workflows. Promoting changes by cloning workflows doesn't scale. Next time I would keep one set of workflows in version control, use environment-specific config, and deploy from there.
  • Deterministic where it matters. The audit's numbers came from plain code with parity tests, and LLMs only handled extraction and writing. That split made the output defensible, and I'd use it again.
