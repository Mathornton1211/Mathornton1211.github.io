How this site's AI works

A portfolio says "I build AI features". This one runs two of them, so you can check. Here's how they're built, and the guardrails that keep an AI on a public page honest, safe, and free to run.

Architecture

The agent

The chat on the home page is a tool-using agent, not a chatbot with a resume pasted into its prompt. It has four read-only tools over profile.json: list_projects, get_project, get_experience and get_skills. It decides what to look up, and you can watch it do so: each tool call is streamed to the page as it happens.

  • Grounded, not memorized. The system prompt tells it to look facts up before answering and to say when something isn't covered. Keeping the facts in tools instead of the prompt means answers cite what the data says, and a new project is one JSON edit.
  • Streaming. The Worker runs the tool loop and re-emits a simple event stream (tool, tool_result, text, done), so the browser code stays about 150 lines with no framework.
  • Bounded. At most three tool rounds per answer, a capped history length, and inputs validated with Zod before any tool runs.

The job tailor

Paste a job description and the tailor returns a typed JSON object: requirements matched with evidence, gaps, a tailored headline and summary, reordered projects, reworded bullets, and a short intro note. It uses the model's JSON-schema mode, and the result is validated against a Zod schema (with one retry), so the page never has to parse free text.

The hard rule is honesty. The model may reword, reorder and cut, but never add. Every project and job id it returns is checked against the profile before it's shown, and the prompt treats the job description as untrusted input, so instructions hidden in a pasted posting are ignored.

Guardrails for a public AI

  • Least privilege. The agent can only read one JSON file. It has no web access, no email, and nothing that writes.
  • Prompt-injection posture. Visitor messages and job descriptions are treated as data. The agent's only capability is reading public facts, so the worst a successful injection can do is make it say something odd.
  • $0 by construction, not by budget. The model runs on Cloudflare Workers AI's free daily allowance, on an account with no billing. When the allowance runs out, calls fail and the page switches to recorded examples: same tool traces, same answers, clearly labelled. A per-IP hourly limit keeps one visitor from using up the day.
  • Origin allow-list. Only this site (and localhost for development) can call the Worker.
  • Prompt leaks are blocked in code. Every answer is checked for fragments of the agent's own instructions before it is sent. Evals showed a prompt instruction alone stopped extraction only two times in three.
  • Measured, not assumed. 36 automated evals cover grounding, hallucination traps and prompt injection, and every answer is published. Public usage counters only count real visitors; eval traffic is excluded.
  • Tolerant of model quirks. Open models return tool calls in slightly different shapes, so the Worker normalizes them and validates every argument before a tool runs. Bad structured output gets one retry, and then the recorded example.
  • Degrades gracefully. If the Worker is down, the chat says so and points to the static content. A mock mode lets the whole site run offline for development.

Why this design

This is the same pattern I'd use for an internal AI feature at work: a thin, auditable service in front of the model, narrowly scoped tools instead of broad access, structured output wherever code consumes the result, and a cost ceiling that is structural rather than a number someone has to watch.
